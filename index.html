Declined Refunds Automation Agent

The problem

Keeping track of declined refunds meant collecting the records from the portals by hand, summarizing them for the team and writing a status email to each customer.

What I built

An agentic system on n8n that owns the whole process. The agent has a tool for every step, and the process is triggered by chatting with it, so an operator can ask it to run the full flow or only one part of it and the agent decides which tools to call.

How it works

  1. Pulls the declined-refund data from the portals.
  2. Stores the records in BigQuery, where they are available for reporting.
  3. Posts a summary of the data to Slack for the team.
  4. Emails each customer the current status of their refund.

Outcome

One chat message replaces a manual chain of copying, summarizing and follow-up emails, and the data lands in BigQuery as part of the same run, so reporting needs no extra work.

HR Contract Renewal Agent

The problem

HR had to watch contract end dates, chase every manager for a renewal decision and then fill each renewal contract by hand.

What I built

A chatbot-style agent that HR triggers on request. It has access to the BambooHR API, email, the Google Sheets that hold the managers' decisions and the employee data, and the contract template.

How it works

  1. Queries the BambooHR API for employees whose contracts end within the next 60 days.
  2. For each of them, emails the employee's manager a form to record the decision: renew or not.
  3. Reads the managers' responses from a Google Sheet.

Outcome

Handles about 30 contracts per quarter and saves HR roughly 10 hours a month.

Wego, 2026 | n8n workflows, GitHub, LLMs

GitHub Pull Request Review Pipeline

The problem

Every pull request needed a first pass before a human reviewer could get to it: what changed, where the risks are and what to comment on.

What I built

A set of n8n workflows that listen for pull request creation on GitHub and run an LLM review automatically.

How it works

  1. A workflow is triggered when a pull request is created and fetches its diff.
  2. The diff is passed to three LLMs that analyze it, summarize the change, look for bugs and write review comments.
  3. The outputs are consolidated and posted back on the pull request in GitHub.

Outcome

Reviewers open a pull request that already carries a summary, a list of suspected bugs and draft comments, and can spend their time on judgment instead of reading every line first.

Ejada Systems, 2025 | Reinforcement learning, Python, R&D

Reinforcement Learning Planner for a Water Desalination Plant

The problem

In a water desalination plant, the times at which valves open and close decide how much chemical treatment is consumed and what the operation costs. The R&D question was: when exactly should the valves open and close, and when should the chemical treatment change, to minimize cost and chemical use while keeping the water output high?

What I built

A reinforcement learning planning system that learns that schedule. I implemented the approach recommended in a published deep reinforcement learning study on this problem (reference paper).

How it works

  1. Plant operation is treated as a sequential decision problem: at each step the agent decides which valves to open or close and which chemical treatment to apply.
  2. The reward favors water output and penalizes operating cost and chemical consumption, so the learned policy trades the two off.
  3. The agent learns by trial and error: it tries schedules, observes the resulting cost, chemical use and output, and improves its policy over time.

Ejada Systems, 2025 | RAG, LangChain, FAISS, code embeddings, FastAPI, Docker

COBOL Code Understanding RAG System

The problem

A bank's core system was written in COBOL across multiple applications. Software architects needed to understand that legacy codebase, ask questions about it and find related scripts without reading everything line by line.

What I built

A Retrieval-Augmented Generation system over the whole codebase with two main applications: a chatbot that answers questions about the code in natural language, and similarity search that finds the scripts related to a given one. The project also produced auto-generated system documentation and an MVP re-implementation in Java and Python.

How it works

  1. Context chunking: each function and code block becomes its own chunk, and an LLM pass captures how every chunk relates to the rest of the script, so a retrieved chunk carries its context instead of being an isolated snippet.
  2. Code embeddings: the chunks are embedded with a code-specific embedding model rather than a general text embedder, so retrieval follows code semantics.
  3. Vector store: embeddings are indexed in FAISS, Meta's vector search library, deployed on the company's own server, with a graph database holding the relationships between code units.
  4. Applications: the chatbot retrieves the relevant chunks and answers the architect's question, and the similarity service compares scripts to surface related code.

Ejada Systems, 2025 | LLM pipeline, RAG, NER, test generation

AI Test Generation Framework (Closed-Box Testing)

The problem

Test cases are usually written after the code exists. The goal here was to generate them before implementation, from the business documents alone (SRS and BRD), which makes it closed-box testing.

What I built

A multi-stage pipeline that combines named entity recognition, several RAG systems and LLM modules, each responsible for one step, plus an evaluation stage that checks the result against the documents.

How it works

  1. Variable extraction: NER identifies the variables mentioned in the SRS and BRD.
  2. Constraint extraction: a RAG system reads the explanations around each variable and derives its constraints, such as the number of characters, allowed ranges and formats.
  3. Test path generation: a second RAG system takes the variables, constraints and documents and generates test paths, each a graph of steps. Positive paths lead to a successful outcome; negative paths violate a constraint and lead to a failure.
  4. Data generation: an LLM takes the variables and their constraints and generates positive and negative data for each path, turning paths into concrete test cases.
  5. Coverage evaluation: a separate LLM-based evaluator compares the generated test cases with the business documents to make sure coverage reaches at least 95%.
  6. After implementation: the framework also generates unit test code for the system's modules.
